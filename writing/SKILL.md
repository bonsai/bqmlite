# W — Writing（文章のための）

W は「書く」を担う層。**読者が読みたい・知りたいと思う文章を、明確な答えとともに生み出す**。

## 位置づけ

```
MX（見つける）→ RX（深掘る）→ AX（任せる）→ W(Writing：書く) → 届ける
```

- W は成果物が「文章」である場合の実行層。
- 起動したら、まず **誰のための文章か（読者）** と **何を伝えるか（テーマ）** を確定する。

## 執筆の3原則

1. **読者目線**：書き手の都合ではなく、読者が「読みたい・知りたい」と思う順に書く。
2. **答えを明確に**：各節・各章に結論（答え）を必ず置く。読者は結論を求めて読む。
3. **層に合わせる**：同じ内容でも読者層（初学者／文系／実務者／教養層）に応じて語彙・例・進め方を変える（ローカライズ）。

## DQ（デベロッパークエスチョン）で書く

問いをタイトルにし、Qで引っかけて、本文で答えを出す。

1. **タイトルは疑問形**：「なぜ？」「どうやって？」「どっち？」で始める。
2. **Qで引っかける**：読者が「あ、これ知りたい」と思う具体的な問いにする。
3. **章の構造**：冒頭でDQ提示 → 本文で候補を比較 → 末尾で答えを1文明示。
4. **答えの型**：「結論：〜ならば◯を選べ」のように、判断が変わる形で締める。

## 文体・表記のルール（既定）

- タイトルは**シンプルな日本語の疑問形**。英語は**副題のみ**に置く。
- エンジニアリングの文脈では、専門用語を一般語に薄めすぎない（あくまでエンジニアリング）。
- 1本のブログは**約1,200字**を基本単位にする（連載・分割に強い）。
- 長い説明は「比喩」「対話劇」「歴史」で読み物化してよい（例：プラトン対話）。
- コードや数値は、主張の証拠として具体的に置く。

## 執筆ワークフロー

1. **WQ（ライティングクエスチョン）を洗い出す** — 執筆者用の内部質問。
2. **DQ に翻訳する** — 読者目線の疑問形タイトルにする（`DQ = WQを読者視線に翻訳`）。
3. **答えを先に1文で決める** — 書きながら迷わないよう、各節の結論を先に確定。
4. **下書き** — 冒頭Q → 比較・検討 → 答えの順で書く。
5. **推敲** — 一文一義、冗長削除、読者層との語彙一致を確認。
6. **ローカライズ** — 読者層別に（帯・まえがき・例・進め方）を差し替える。
7. **届ける** — 公開・販売・配布の導線へ渡す。

## 文章チェックリスト

- [ ] タイトルが疑問形（DQ）になっているか
- [ ] Qで「読みたい・知りたい」を引っかけているか
- [ ] 各節の答えが1文で明示されているか
- [ ] 読者層（初学者／文系／実務者）に語彙が合っているか
- [ ] 英語が必要以上に本文に混ざっていないか（副題へ）
- [ ] 具体例・数字・コードなど証拠があるか
- [ ] 冗長な前置き・重複を削ったか

## 注意

- 市場との関係設計や販売戦略は MX のスキル（`mx`）で扱う。
- エージェントの能力・タスク定義は AX のスキル（`ax`）で扱う。
- 仕事全体の流れ（見つける→深掘る→任せる→生み出す）は WX のスキル（`wx`）で扱う。
